    The local-first system I actually run

    November 17, 2026 10 min read

    Everyone argues about local-first in the abstract. I run one without calling it that, and the vault I am writing this in is the system the post describes. So instead of making the case for it, here is what it has cost and what it has paid back, with dates.

    The system

    My notes are a folder of markdown files: one topic per file, kebab-case names, a few lines of YAML frontmatter at the top. They live in a git repository with a remote on a Gitea server in my homelab. There is no database. The first commit is dated 2026-06-09, and the history has 161 commits today.

    Local-first fell out of two choices

    Nobody built local-first here. It comes from two choices: files and git. Files mean the thing I read is on the disk in front of me. Git means sync is a pull and a push, and a push that fails is something to do later.

    The clearest case so far came on 2026-11-05. An agent running under Claude Code on my Mac could not reach the vault’s remote. Git’s HTTPS helper failed with “Couldn’t connect to server” after about 4 ms, while curl to the same host from the same shell got a 200. By the next day the cause was narrowed down. macOS Local Network privacy blocks git’s HTTPS helper when it runs as a child of the claude process, and System Settings has no entry to grant. The same git fetch worked fine from a plain terminal tab.

    The vault’s entry file already has a policy for this: pull first, and if git cannot reach the remote, work locally and say the push is pending. On 2026-11-06 the remote moved to SSH on port 2222, which the harness can reach, and pull and push now work from the harness and from a plain terminal alike. The block cost me a transport fix. It never cost me access to anything I had written.

    What it bought me

    It outlived its tools

    The record is short, months not years, so I will claim only what it shows. The pipeline that turns vault notes into blog posts was first built on n8n, and it called models through a LiteLLM gateway. Both are gone. Airflow runs the pipeline now, triggered by a Gitea webhook, and model calls go through OmniRoute. The notes did not change for any of it. The folders are the same as before: 1_ideas/, 2_drafts_for_review/, 3_ready_to_publish/.

    This post is part of the evidence. Its first draft was n8n output from June, and that draft was deleted on 2026-11-12 so the idea could go through the new pipeline. The pipeline was replaced, and the idea note it read was not.

    It was readable by things I did not plan for

    The vault’s root CLAUDE.md opens by saying the vault is designed to be read by LLMs as long-term memory. That line came after the files did. They were plain text in a folder, so pointing an agent at them took no integration work.

    Today three agent harnesses share it: Claude Code, OpenCode and Hermes. Each one reads the same entry note at the start of a session and writes back what it learns. The git log shows this: 32 commits are authored by “Hermes Developer” and 2 by “airflow-agent”, the pipeline’s publish step, alongside my own.

    The example I like best is about where memory used to live. My standing rules for coding agents (do your own git, verify before fixing, never print secrets) built up as corrections in Claude Code’s auto-memory, under ~/.claude/projects/*/memory/ on one machine. No other harness could read them. Once I used more than one harness, that store was a dead end. On 2026-11-10 the rules moved into a vault note, agent-working-agreements.md, and every harness reads them now. The machine-local store needed a migration. The vault never did, because there was never anything to export from.

    Offline is not a mode

    There is no offline mode to enter and no degraded state to handle, because nothing I read is remote. The November block made the point better than an argument could. For one harness the remote was out of reach for about a day, and what that meant was a push marked as pending. It was a to-do, not an outage.

    Where it is genuinely worse

    This section is not softened.

    • Conflicts are mine. When two writers touch the same lines, git gives me a conflict marker, not a merge. CRDT-based tools do this better, and I am choosing the manual version. To be accurate: the log has no merge commits, because the policy is pull --rebase, and I have no record of resolving a conflict in this vault. That comes from luck and low concurrency, not from a solution. Several agents now write to the same repository, so this is a risk I carry, not a cost I have paid yet.
    • There is no sharing story. Showing someone a note means sending a Gitea link to a repository they cannot open, or copying the text out by hand. It has to stay that way. The vault holds personal records and identifiers, so the repository stays private. The same privacy that makes it useful as memory rules out sharing it.
    • Search is only as good as my tools. Nobody runs an index for me. The index is Engineering/scripts/build-index.py, a script I run that writes Engineering/index.json. It is hardcoded to Engineering/, so the newer Research/ folder has no manifest at all. Beyond that, search is grep.
    • It assumes git literacy. That rules this approach out for most people, and the trade is not free. Even with the literacy, it broke. Under an agent harness the HTTPS transport failed in a way no settings pane could fix, and the SSH key that fixed it had to be made by hand, because the harness’s safety rules refuse to generate one.
    • I committed the wrong things anyway. The working tree is about 5.7 MB, but the git pack is about 16 MB. Nearly all of the difference is ten PNGs, about 16.6 MB raw, from one June afternoon. Trigger pings to the old image pipeline kept committing generated images into this repository, under the same subject again and again: ‘chore: add AI generated image 2’. Every one of them had garbled lettering in it. Most were deleted two days later, and git history kept them anyway. The rule below exists partly because I broke it.

    The rule that changed my mind

    The rule I ended up with is not ‘keep everything local’. It is this: memory is plain files; everything else can be a service. That is a decision about where things belong. It is not a position on cloud versus local.

    The clearest application was the paperwork for one piece of equipment I own. The vault once held 70 files for it: 36 PDFs, 22 firmware images and some audio test media, 553 MB in all. They became one markdown note, recorded at 16 KB at the time, holding the facts worth keeping: registration, a service table, recalls, parts. The originals live on my NAS. The note carries a single source-root that points at the NAS folder, and every original it cites resolves under that root. Before anything was deleted, each file was compared to its NAS copy by sha256, not by name or size, because binaries git never tracked have no history to recover from. The conventions also separate records from tools. Invoices and manuals carry facts worth extracting. Firmware and test signals do not, so the note says what they are and where to get them again, and does not pretend an extraction happened.

    I considered Git LFS and did not need it. The note I wrote that day says why: binaries do not belong in the vault at all, and the problem was never that they needed better storage. The same reasoning limits each note to one source-root, because a second root is a filing problem wearing a syntax solution.

    The NAS holds the evidence. The note holds the facts. That split keeps the repository small enough to check out wherever an agent runs, and it is the decision I would defend hardest, more than markdown or git. It is the same idea I use at the architecture level: the artifact is canonical, and anything derived from it is cache. It also matches how I decide what to run myself: size the gap rather than follow an ideology, because owning something is a running cost. The NAS is a service to the notes. Moving it would mean changing one line per note.

    This shape has a name

    Andrej Karpathy has described almost exactly this arrangement, as an LLM wiki: not a product, a method. Three layers. Raw sources the model reads and never modifies. A wiki of markdown files the model owns and maintains, which is what you actually read. And a schema document that defines the conventions, which you and the model refine together.

    Mapped onto what I run, the correspondence is almost line for line. The NAS is the immutable source layer. The notes are the wiki. The schema document is literally a CLAUDE.md at the root of the repository, which is where the naming rules, the frontmatter contract and the one-source-root rule live. Retrieval works the same way too: no vector database, no embedding step. An agent reads the index first and then opens the pages it names. The gist says this works at moderate scale, a hundred sources and a few hundred pages, which is roughly where I am.

    I am not claiming I derived it. The interesting part is that the pattern is convergent — pick plain files, a git repo and an agent that can read a folder, and you arrive here whether or not anyone has written it down for you.

    Two differences are worth stating, because they are where the idea meets friction.

    The gist is explicit that it describes an idea rather than a tested implementation. This post is the other half of that: a year of it running, and the specific failures are the parts worth reading — the git pack that grew to three times its working tree, the transport that broke under an agent harness, the conflicts I have not had yet and will.

    The sharper critique of the pattern is that compiling sources into a wiki loses fidelity: the summary keeps what you thought mattered on the day you wrote it. That is true, and it is why the source-root convention exists. The note is not a replacement for the original, it is an index into it, and every fact it carries cites the file it came from. Compression you cannot reverse is a different thing from compression you can. The sha256 check before deleting anything is the same instinct: the compiled layer is allowed to be lossy only because the source layer is intact.

    The point

    Local-first is usually argued as a stance on ownership. What I got was optionality. The notes were in the dullest format I could pick, so tools I had not planned for could use them: three agent harnesses, and a publishing pipeline now on its second orchestrator. The ownership argument is true, but it is not what paid off. Being boring is what paid off.
